An agent is a harness plus a model. `-a` names the harness, `-m` the model it drives. Seven harnesses are built in.

| Name on `-a` | Harness |
| --- | --- |
| `claude` | Claude Code |
| `codex` | Codex |
| `gemini` | Gemini CLI |
| `qwen` | Qwen Code |
| `kimi` | Kimi Code |
| `opencode` | OpenCode |
| `droid` | Droid |

```bash
evolve run \
  -d terminal-bench-4@4.0 \
  -a claude \
  -m fable \
  -l 5 \
  --watch
```

`-a <name[@version]>` can pin a harness version. Omitted, the latest is resolved once, when the job is created, and stamped on the arm, so a vendor release mid-job never splits one job across two versions. The version that actually ran is recorded on every trial as `agent_info.version`. A pin that does not resolve is refused with `agent_version_not_found`, a failed lookup of the latest with `agent_version_unresolvable` (retry the create), and a pin on a registered agent is refused, because registered agents are versioned by their own content.

## Configure the arm

These flags apply to every arm of the job.

```bash
evolve run \
  -d terminal-bench-4@4.0 \
  -a codex \
  -m gpt-5.5 \
  -l 5 \
  --effort high \
  --preset no-internet \
  --ak config=./codex-settings.json
```

`--effort <value>` sets the reasoning effort; see [models](/core-concepts/models#reasoning-effort). `--preset <name>` applies a named settings bundle: `no-internet` turns the vendor's server-side web tools off (Claude gets a settings `permissions.deny` for WebSearch and WebFetch, Codex `web_search=disabled`), `pinned-context` fixes the context window at 200000 tokens. A preset sits on top of any `--ak config` document and wins where they disagree. `--ak config=<path|inline JSON>` becomes the harness's native settings file inside the sandbox; your document is the base and the platform's routing sits on top. The config and the preset are part of the arm's identity, and the job body echoes them as `kwargs` and `preset`.

Only `claude` and `codex` take a config or a preset; each harness's entry in the [capability document](/sdk-reference/meta) publishes `supports_config` and `presets`. An effort or preset a harness cannot honor is refused when the job is created, never silently skipped: `agent_preset_unsupported`, `agent_config_unsupported`, `agent_kwarg_unsupported` for a key other than `config`, and `agent_config_key_refused` for a config key that touches billing, base URLs, routing or environment.

Environment for the agent comes from two places, and a job cannot add a third: a task's own `[environment.env]` table, and a secret attached with `--secret`. The server refuses `agent_env` (the `--ae` flag) on job create. See [secrets](/core-concepts/secrets) and [tasks](/core-concepts/tasks#environment-variables).

## Register your own agent

Any CLI can run as an agent. Register it once, and its name works on `-a` like a built-in.

```bash
evolve agent add acme-cli --install-script ./install.sh --run "acme-cli --headless"
evolve run \
  -d terminal-bench-4@4.0 \
  -a acme-cli \
  -m gpt-5.5 \
  -l 5 \
  --watch
```

`--install-script <path>` names a file; its contents are uploaded. `--dir <path>` uploads a local directory instead. `--run <command>` is required and runs with `sh -c`. `--ae KEY=VALUE` injects environment at run time and may repeat.

```bash
evolve agent list
evolve agent show acme-cli
evolve agent remove acme-cli
```

Removing an agent keeps the record of the past jobs that ran it. Registered agents are private: another account's name reads as `agent_not_found`. The number you may hold is published as `agent_registration.max_per_user`; past it, registration is refused with `agent_limit_reached`.

### How it is built

The install script, or the uploaded directory, runs once in a throwaway builder sandbox that has internet and no secrets. Everything it fetches must be publicly fetchable, and it must leave its executables in `$PREFIX/bin`. A registered agent is versioned by its content, the install source, the run command and the declared env together; change any of them and the next run installs the new version. To change one without a gap, use `upsert` rather than remove and add.

### The run contract

Your `run_command` runs with `sh -c` at the task's working directory, and can rely on exactly this:

- The instruction arrives twice: on stdin, and at the path in `$EVOLVE_INSTRUCTION_FILE`.
- `$EVOLVE_GATEWAY_BASE_URL` is an OpenAI-compatible base URL that already ends in `/v1`, and `$EVOLVE_GATEWAY_API_KEY` is its credential. The same two values are also `$OPENAI_BASE_URL` and `$OPENAI_API_KEY`, so a CLI that reads its endpoint from the environment works unchanged.
- `$EVOLVE_MODEL` is the `model_name` of the arm.
- Your declared env is injected at run time and may not override those six keys; registration refuses that with `agent_invalid_env`, and refuses a credential-shaped key the same way.

A CLI that routes through a config file must write that file inside `run_command`, from the contract values; it cannot be written at install time, because the install ran in a different sandbox. `codex` is the worked example:

```bash
mkdir -p ~/.codex && cat > ~/.codex/config.toml <<EOF
model_provider = "evolve"
[model_providers.evolve]
name = "evolve"
base_url = "$EVOLVE_GATEWAY_BASE_URL"
env_key = "EVOLVE_GATEWAY_API_KEY"
wire_api = "responses"
EOF
codex login --with-api-key <<< "$EVOLVE_GATEWAY_API_KEY"
codex exec --skip-git-repo-check -
```

A CLI that ignores `OPENAI_BASE_URL` without this will try its vendor's endpoint, find the box sealed, and spend the whole agent budget failing to connect.

The spend cap is enforced on the gateway key. What keeps traffic on that route is the task's network policy, not the agent: under `no-network` the cap is a hard guarantee, under `allowlist` or `public` an agent can reach a provider with a key of its own, unmetered. See [models](/core-concepts/models).

What a registered agent gives up against a built-in: no live trace events (there is no parser for an unknown CLI), no live spend or token reading (`live_spent_usd` stays null until settle), and no `reasoning_effort` (an effort on the arm is recorded but never reaches the command; put the flag in `run_command`). Everything else, the patch, the verifier, the artifacts, the timings, the settled spend, is recorded as for a built-in.
